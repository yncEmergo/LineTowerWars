# Playtest 8: playtest 7's freezes again, on a build that predates their fix

**2026-09-15**, about a session played on the evening of 2026-09-14. Three players - the user
(Milo), Siggi (Siegfried) and a third (AFDIstScheisse / Offen) - against the rented relay, in four
matches. Logs came from the user and Siggi only. Reported: Siggi lagged at the start of the first
longer match and had no complaints afterwards, while the user did not lag at all.

Asked: why Siggi lagged, network or performance; what would make the next session's logs more
useful; and how much of the rented server a match uses, and whether it could run several lobbies
at once.

**Short answer: it was his own machine, not the network.** He was compiling shaders the first
time each kind of tower was drawn, exactly as in playtest 7. **The build everybody played was
`b900267`, the commit BEFORE `d1e2e49`**, which added `ShaderWarmup` and seal repair. So the fix
has still never been in a tester's hands. The server was on `b900267` as well, which is why
nobody was refused at connect.

## How it was read

- **Every file there was**: the user's and Siggi's session logs and Godot logs, the relay's
  journal for the evening (`journalctl -u ltw-server`), and the relay box's own `sar` history
  (`/var/log/sysstat/sa14`, ten-minute averages).
- **One throwaway script** in the session scratchpad, with nothing in the repo. It takes each
  player's `turn.state` lines (one every ten turns) and finds windows that took more than 0.75 s
  where 0.5 s is normal. It aligns stalls by TURN across both players, and tests whether each
  stall comes right after a build or upgrade into a kind of tower that match had not had yet.
  Ability ids were resolved against `b900267`'s `.tres` files, not HEAD's.
- **Aligned by turn number, not clock.** Both logs carry turn numbers, so the machines' clocks
  never had to agree. The relay journal was aligned by its own UTC stamps against the session
  headers' `utc`.

## 1. Siggi's lag was local

**His link was clean all evening.** Across every health line in both of his matches: round trip
20-26 ms after the first seconds, `echo` recovered **0**, and seal arrival `max` never more than
7 ms late. The user's link, in the same matches, recovered a handful of lost seals and was still
fine.

**His stalls were a machine stopping, not seals arriving late.** Each one ended with a backlog:
`held` of 7, 8, 12 and **16 turns** behind the stall, at 50 ms a turn. A backlog like that
builds up while seals keep arriving and nothing plays them. It is the same signature playtest 7
called local.

**The user's machine hitched at none of those turns.** Every peer simulates every lane, so a
simulation cost would have hit both on the same turn.

| | stalls | 10-turn windows over 0.75 s | largest backlog after a stall |
| --- | --- | --- | --- |
| user, match-6 | 2 | 0 | 4 |
| Siggi, match-6 | 20 | 6 (worst **1.32 s**, 11 s into the match) | 16 |
| user, match-7 | 1 | 0 | 0 |
| Siggi, match-7 | 7 | 0 | 9 |
| Siggi, match-8 (Godot log only) | 6 "Waiting on a turn" warnings | - | - |

"No complaints later" matches this: match-6 was bad, match-7 was mostly smooth, and match-8, in a
fresh process, was quiet too. Godot keeps compiled shaders on disk in `user://shader_cache`, so
each shader is paid for once per machine.

### What set each freeze off

Siggi's match-6 stalls with a backlog of 7 or more, which are the ones long enough to notice:

| stall turn | backlog | right before it |
| --- | --- | --- |
| 157 | 16 | the match's first Lesser Archers (turns 152, 154) |
| 718 | 8 | first creeps in his lane, and his own first build (the ghost is shown before the order) |
| 1630 | 7 | the first Lesser Cutters under construction (ordered at turn 1563) |
| 2999 | 8 | first upgrade into an Archer (turn 2997) |
| 5184 | 7 | his own first Elemental Core (turn 5181) |
| 7716 | 7 | first Magma Well (turn 7714) |
| 8161 | 7 | not identified |
| 15257 | 7 | first Technology Disc (turn 15238) |
| 15880 | 12 | the user's cheat LOAD LAYOUT, which put a whole maze down in one turn (below) |

**Five of the nine follow a first-of-its-kind build or upgrade within twenty turns**, and two more
are the first creeps and the first construction. Of the 25 kinds first built in match-6, most
arrived with no stall at all. That is playtest 7's pattern too: only a kind that brings a new
shader freezes. The user's machine is the dev PC, with everything compiled long ago, and did not
stall after any of them.

**Not proven here:** that each freeze is a shader compile rather than some other first-draw cost.
The logs cannot say. What they do show is the timing and the local signature, and
`ShaderProbe` already reproduced this exact freeze at up to a second on the Archer. What would
settle it is the next playtest's `match.shaders_warmed` line and the frame-hitch line proposed
below.

### The one hitch both machines shared

At turn 15874-15875 the user pressed the cheat that saves and reloads a layout. The reload carries
the whole maze in one order. The relay logged `Sending 2708 bytes unreliably which is above the
MTU (1392)` from `_seal_stream` at 20:08:39, which is match-6's start plus 794 s, turn 15875. So
the echo of that seal went out as a fragmented datagram. Both peers stalled there: the user
briefly, and Siggi for 1 s with a 12-turn backlog, since he also had to draw a whole new maze. It
is a cheat path, but it shows a big order can outgrow a packet. A real feature that puts many
towers down in one order would do the same.

## 2. The server

A 2 vCPU Skylake VPS with 3.8 GB of RAM and no swap. The relay process had been up since
2026-09-10 15:37 UTC, running `b900267`.

### What a match costs it

| | measured |
| --- | --- |
| whole box, CPU, before the session (19:40) | 2.1% of both cores |
| whole box, CPU, busiest ten minutes of a 3-player match | 2.9% |
| relay process, idle, 30 s sample on 2026-09-15 | 2.7% of one core |
| relay process, lifetime: 11,901 CPU-seconds in 5 d 2 h | 2.7% of one core on average |
| memory used by the box, lobby vs. in a match | 284 MB vs. 354 MB, of 3.8 GB |
| relay resident memory, idle | 207 MB |
| network out, 3-player match, busiest ten minutes | 16 kB/s (about 130 kbit/s) |
| network in, same | 4.7 kB/s |
| network out, 5-player match on 2026-09-10 | 18.5 kB/s |

**Derived from those numbers:** almost all of the relay's CPU goes to its capped idle loop, not
to matches. Its lifetime CPU is what the idle rate alone predicts, to within 33 CPU-seconds, over
about 88 minutes of matches, so a match costs too little to separate from idle at this
resolution. **The share of the server in use during this playtest was about 3% of the CPU, under
10% of the memory, and a negligible slice of the bandwidth.**

### Several lobbies at once

**The hardware is not what stops it. The code is.** The server can already hold several lobbies,
but only one of them can be IN A MATCH: `LobbyService` refuses a second Start with "The server is
already running a match." (D19). Nothing about the box forces that.

Rough headroom, **inferred, not load-tested**:

- **One process per match (D16):** memory is the limit. At about 200 MB a relay against 3.1 GB
  available, that is on the order of ten matches, and the idle loops would cost about 3% of a
  core each.
- **Several matches in one relay process:** CPU would be the limit, and by the numbers above a
  match costs a small fraction of one core. The box would run out of players long before cores.

Either way, bandwidth is not a concern at these rates.

What it would take is software. `multiplayer.md` already lists "one process per match" as open.
Its §11.3 notes that D16's original reason, using more cores, died when the server stopped
simulating, so the choice is now about isolation versus simplicity. A second relay on port 7778
works today with no code, but a client dials the first address that answers, so nobody would
reach it without `--address`/`--port`.

## 3. What would have made these logs better

In order of what they would have saved this investigation.

1. **Ship the build that already has the diagnostics.** HEAD's session log carries
   `match.shaders_warmed`, `repair`, `link` and the relay's per-player link report. None of it was
   in playtest 8 because the build was four commits old. Before a session, check that the menu
   corner's build is HEAD and that `deploy_server.ps1 -Check` agrees.
2. **Session logging on by default in a playtest build.** It is opt-in per process, and that cost
   Siggi's match-8, both of match-5's other logs and everything from the third player. The
   opt-out could stay; old files rotate out the way Godot's own logs do. `MatchRecorder` already
   records every match unasked, so the precedent exists.
3. **A `frame.hitch` line**: any frame over roughly 100 ms of wall clock, with its length and the
   turn. Every "local freeze" above was inferred from the backlog left behind. One line would
   measure it. Counting `user://shader_cache` files before and after a hitch, the `ShaderProbe`
   trick, would also say whether that hitch compiled a shader. The count only needs taking when
   a hitch happens.
4. **A turn number on `lockstep.catchup`, and a line when a stall ENDS** with how long it held.
   Today a stall's start has a turn, and its cost has to be reconstructed from the catch-up lines
   that follow, which have no turn at all.
5. **The machine in the header**: GPU and driver, CPU and core count, RAM, resolution, refresh
   rate, vsync and frame cap. The GPU name was only in the Godot log.
6. **The roster in `match.starting`**: slot, name and peer id. Here "slot 3" had to be matched to
   a person through the relay journal.
7. **A per-match summary on the relay**: length, turns sealed, bytes in and out per peer, the
   largest seal, how many sends exceeded the MTU, and the process's CPU-seconds and memory at the
   end. With it, the capacity question is answered from the journal instead of from `sar`. The
   oversized-send warning should also name its turn: here it could only be matched by clock.
8. **Less noise in the Godot log.** Each match start prints 180 "invalid UID" warning lines, three
   times in one Godot log here, still open from playtest 7. The Godot log also has no timestamps,
   so only the lines carrying a turn number could be aligned with anything.

Worth measuring rather than assuming if (2) happens: the session log flushes on every line. That
was deliberate, to keep a crash's tail. **Measured the same day** on the office PC (Windows,
throwaway project, 5,000 lines of a real turn line): 0.3 us a line unflushed, 1.9 us flushed. At
a few lines a second that is nothing, so the flush stays. Two megabytes over a 45-minute session
is not a size problem either.

## What was changed

Amended the same day, after the user asked for the logging items above to be built. Items 2 to 7
are in; item 1 is a process, not code; item 8 is half done.

- **On by default.** `Boot` opens the session log for every windowed client when
  `NetworkConfig.session_log_on_by_default` says so. Opening a file prunes the folder to
  `session_logs_kept`. Headless runs never open one by default. The lobby box still turns it off.
- **`frame.hitch`** for any frame of `hitch_threshold_ms` or longer, with its length, turn,
  whether the warm-up was running, whether the window had focus, and how many shader-cache files
  appeared since the last count. Capped per few seconds. The health line gains `frame`: fps,
  worst frame, hitch count, draw calls, nodes and memory.
- **`lockstep.resumed`** when a stall ends, with `held_ms` and `backlog`, through the new
  `LockstepService.turn_resumed` signal. `lockstep.catchup` carries `turn`.
- **The `machine` line** in the header (CPU, cores, RAM, GPU, vendor, driver, API, renderer,
  shader-cache size), and `process_msec` in `session.begin`.
- **`match.starting`** carries the roster (slot, name, peer, AI), the display (window mode and
  size, screen, refresh rate, vsync, frame cap) and the shader-cache size.
- **`Relay match summary`** in the journal when a match ends: length, turns, orders, largest seal
  and its turn, oversized seals, worst tick, late ticks, repairs, CPU-seconds and share of a core,
  resident and static memory, and bytes and packets both ways. A new
  `A seal is too large for one packet` warning names the turn. See `RelayMatchStats` and
  `NetworkService.pop_traffic`.
- **Godot log lines are stamped** in milliseconds since process start on a client. The session
  header's `process_msec` joins the two files.
- **Not done: the invalid-UID warnings.** The source `.tres` files carry no uid and the export
  invents them, so the fix is in how content is saved and generated, and it can only be proven by
  an export. That is a build-time task, not a logging one.

Checked with the probe harness: a relay and two headless clients on loopback, 25 s, session
logging on. Every new line fired: a stall that ended after 767 ms with a backlog of 1, a 102 ms
hitch, the roster, and a relay summary of 97 kB sent and 15 kB received over 496 turns. A short
windowed run confirmed the log opens by itself, and that the machine line names the RTX 4080 and
its driver. The CPU and memory reads were run separately with the relay box's own Godot binary,
because Windows has no `/proc`. The run printed three `Unable to send packet` errors from
`LobbyService` pushing a lobby to a client that had just quit. That depends on which probe exits
first: an unmodified-HEAD run had the other client leave first and printed none. Not chased.

## What is still open

- **A client build from HEAD, and a deploy to match.** The protocol changed in `d1e2e49`, so the
  two must move together.
- **Whether `ShaderWarmup` removes these freezes on a cold AMD machine.** Siggi's cache is warm
  now, so he is no longer a clean test. A new tester, or a moved-aside cache, would be.
- The invalid-UID warnings in an exported build (item 8).
- One process per match, or several matches per relay, if concurrent lobbies are wanted.

## Traps

**CHECK WHICH BUILD A PLAYTEST RAN BEFORE READING IT AGAINST HEAD.** The obvious reading of
these logs is "the playtest 7 fix did not work". The session header's `build` field is what
says the fix was never there.

**A FROZEN MACHINE AND A SLOW LINK LOOK DIFFERENT IN `held`.** A peer stopping piles up a backlog
in one go, 7 to 16 turns here. Ordinary pacing on the same link sat at 2 to 3, and a late seal
arrives with nothing queued behind it. Reading the size of the backlog after a stall was enough
to call this local before any other evidence.
